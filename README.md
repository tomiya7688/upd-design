# UPD Design

UPD Design は、アプリケーションの仕事を **UI（利用者とのやり取り）・Process（アプリの判断や計算）・Data（データの取得や保存）** に分ける設計です。

このリポジトリでは、`upd-commander-base-design` をもとに、**Commander を前提にしない UPD の設計**を整理します。各層の中を、特定の名前のクラスや決まった呼び出し構造にそろえることは求めません。

> 層ごとの仕事は分ける。層の中で処理を組み立てる方法は固定しない。

## まず、3つの担当に分ける

商品を検索するアプリなら、次のように分けます。

| 層 | 担当する仕事 | 商品検索の例 |
| --- | --- | --- |
| UI | 入力を受け取り、結果を表示する。 | 検索欄から文字を読み、商品一覧を表示する。 |
| Process | アプリのルールに従って判断し、処理を進める。 | 検索条件を確かめ、必要な商品の取得を依頼する。 |
| Data | データを取得し、保存する。 | データベースやファイルから商品を読み出す。 |

UI は Data を直接呼びません。データが必要なときは、Process を通します。

```text
要求：UI → Process → Data
結果：Data → Process → UI
```

Data が不要な処理は、UI と Process だけで完結できます。表示の切り替えなど、表示だけに関わる仕事は UI の中で完結できます。この図は要求と結果の流れであり、互いの内部実装を自由に参照してよいという意味ではありません。

## Commander base を除く、ということ

Commander を各層に置くことや、すべての処理を Commander 経由にすることを必須にしません。ただし、**Commander を使うこと自体を禁止する設計でもありません。**

本初版では、Messenger（層間の要求や結果を運ぶ役割）も、必須の部品ではなく実装上の選択肢として整理しています。この点と、層をまたぐ呼び出し方の詳細は、[元の設計との差分と検討事項](docs/differences-from-commander-base.md)に記載した初版の整理方針です。

## 現在の範囲

この初版は、設計文書のたたき台です。アプリケーションの実装、元のリポジトリの全仕様、設計を自動確認するチェッカー、開発補助ツールは移植していません。文書に出てくる関数名や構成例は説明用であり、実装済みの機能ではありません。

元のリポジトリのファイルを削除・変更するのではなく、このリポジトリで独立した文書として整理します。元資料と参照した版は、[差分の文書](docs/differences-from-commander-base.md)に記録しています。
