# UPD Design の基本規則

この文書は、UPD Design の初版で守る条件と、実装上の選択肢を整理したものです。設計の背景は[設計の全体像](../docs/architecture.md)、元の仕様との対応は[差分の文書](../docs/differences-from-commander-base.md)を参照してください。

**状態：初版のたたき台です。** 元の設計から引き継ぐ基本規則と、Commander を前提にしないための整理方針を分けています。元のリポジトリの仕様やチェッカーとの完全な互換性を宣言する文書ではありません。

## 1. 規則の強さ

**必須規則**は、この初版で UPD の基本条件として扱うものです。「してはいけない」と書いた条件は、単なる推奨ではありません。

**推奨事項**は、設計を保ちやすくするための方針です。別の方法を採る場合は、その理由と影響を説明できるようにします。

**実装例**は、考え方を説明するための例です。関数名、型名、フォルダ名、処理件数などを、そのまま必須規則にはしません。

## 2. 引き継ぐ基本規則

### 2.1 仕事を UI・Process・Data に分ける

UI は利用者との入出力と表示、Process はアプリの判断と計算、Data はデータの取得と保存を担当します。必要な仕事を、それに対応する層へ置きます。

UI に業務やゲームのルール上の最終判断を置いたり、Process に描画や保存先の操作を置いたり、Data に画面操作や業務上の判断を置いたりしてはいけません。

表示だけに意味がある判断は UI、保存形式に必要な変換は Data が担当できます。「判断」や「変換」という単語だけで所属を決めず、何のための処理かで判断します。

### 2.2 UI と Data は直接やり取りしない

層をまたぐ要求と結果は、次の境界を守ります。

```text
UI ↔ Process ↔ Data
```

UI → Data の直接要求と、Data → UI の直接返却は禁止します。UI が Data の実装を直接参照することも禁止します。共有領域や共通の通知機構を経由して、実質的にこの境界を飛び越える構成も認めません。

### 2.3 各層の実装上の都合を、ほかの層の仕事にしない

Process は画面部品、表示形式、ファイルパス、データベースの接続方法を担当しません。Data は UI の表示処理や Process の業務判断を呼び出して、処理を代行させる構成にはしません。

UI フレームワーク固有のオブジェクトは、そのまま Process へ渡さず、境界で受け渡せる値に変換します。表示や保存に固有のライブラリは、それを必要とする層の内部で扱います。

### 2.4 共有領域で境界を迂回しない

`Common` / `Shared` は任意の共有領域であり、4つ目の処理層ではありません。特定の層の仕事を持たない値、型、受け渡しの定義などを置けます。

UI・Process・Data から共有領域への参照は認めます。共有領域から各層の具体的な実装への依存は禁止します。描画、業務やゲームの処理、データの読み書きを共有領域へ移してはいけません。

### 2.5 戻り値にも同じ境界を適用する

Data からの結果は Process が受け取り、Process からの結果は UI が受け取ります。失敗の通知でも同じです。Data が画面を直接更新したり、Process が UI の表示方法を決めたりしてはいけません。

## 3. Commander を前提にしないための整理方針

この節は、「Commander base を除く」という依頼を、本初版でどう具体化したかを示します。特に Messenger の扱いと公開された窓口の直接呼び出しは、今後確認する設計判断です。

### 3.1 特定の役割を持つクラスを必須にしない

各層に Commander を配置すること、Commander が必ず処理を選ぶこと、呼び出しの整理と実処理を必ず別クラスにすることは求めません。

Messenger の配置と、Messenger 同士を通る固定の経路も、本初版では必須にしません。処理の窓口を Messenger という名前で実装することは可能です。

Commander や Messenger を任意で採用する場合、その詳細な役割分担は採用するプロジェクト側で決めます。採用の有無にかかわらず、2節の基本規則は守ります。

### 3.2 隣り合う層には、公開された窓口から依頼する

UI は Process の公開された窓口を、Process は Data の公開された窓口を使う構成を選べます。窓口は通常の関数やインターフェースでもよく、専用の中継クラスは必須にしません。

この整理方針では、相手の非公開の変数や内部処理へ直接依存しないことを条件にします。Commander を除くことを、別の層の中身を自由に操作できるという意味にはしません。

### 3.3 通信方式とコード上の参照を区別する

関数呼び出し、通知、非同期処理などの方式は固定しません。方式にかかわらず、UI と Data の直接のやり取りは禁止です。

結果が Data → Process → UI と戻ることは、下流の層が上流の具体的な実装へ依存する許可ではありません。呼び出しと、`import` などのコード上の参照の両方で境界を確認します。

## 4. 推奨事項

ひとつの関数やクラスの目的を短い言葉で説明できる大きさに分けることを推奨します。ただし、本初版は行数や関数数による合否基準を定めません。

層の窓口では、受け取る値、返す値、失敗時の扱いを明記することを推奨します。UI の表示テスト、Process の判断や計算のテスト、Data の取得・保存のテストを、それぞれの担当に合わせて用意することも推奨します。

## 5. 適用上の制約と未定義の範囲

移行中などの理由で必須規則を守れない部分がある場合は、理由、対象範囲、影響、解消条件を記録してください。その記録だけで、規則を満たしたことにはなりません。

複数のアプリケーションにまたがる境界、並行処理、トランザクション、チェッカーの判定番号や設定形式、旧チェッカーとの互換性は本初版では定義しません。必要に応じて、Commander に依存しない形で別途整理します。
