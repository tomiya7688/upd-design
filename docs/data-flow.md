# 要求と結果の流れ

この文書は、ひとつの操作が UI・Process・Data をどう通るかを説明します。Commander や Messenger を置かない構成を、説明の例に使います。ここに出てくる窓口の名前は実装例であり、必須の名称ではありません。

## 商品を検索する

```text
利用者が検索ボタンを押す
  → UI が検索欄の値を取り出す
  → Process が検索条件を確認する
  → Data が条件に合う商品を取得する
  → Process がアプリとしての検索結果をまとめる
  → UI が商品一覧を表示する
```

**UI から Process へ。** UI は「商品を検索する」窓口にキーワードを渡します。入力欄そのものや、画面のイベントオブジェクトは渡しません。

**Process から Data へ。** Process は条件を確認し、取得が必要なら「条件に合う商品を取得する」窓口を呼びます。検索条件を満たさない場合は、Data を呼ばずに結果を UI へ返せます。

**Data から Process へ。** Data は商品を取得し、受け渡し用の値として返します。画面表示や検索失敗の案内文は作りません。

**Process から UI へ。** Process は商品の一覧や、検索が成立しなかった理由を返します。表示する文言、配置、色は UI が決めます。

たとえば、受け渡す内容は次のように整理できます。

| 境界 | 渡す内容の例 | 渡さないものの例 |
| --- | --- | --- |
| UI → Process | 検索キーワード。 | 入力欄やボタンのオブジェクト。 |
| Process → Data | 確認済みの検索条件。 | 画面の表示色やレイアウト。 |
| Data → Process | 商品の識別番号、名前、価格。 | データベースの接続オブジェクト。 |
| Process → UI | 表示対象の商品、結果の種類。 | 保存先の操作を UI に任せるための部品。 |

具体的な型、価格の表現、件数の制限などは、機能ごとに決める事項です。この表は、その詳細を規定するものではありません。

## データを保存する

保存ボタンを押した場合も、UI は Data を直接呼びません。

```text
UI：保存したい内容を Process に渡す
  → Process：保存してよい内容か確認し、保存を依頼する
  → Data：保存し、成功または失敗を Process に返す
  → Process：アプリとしての結果を UI に返す
  → UI：結果を表示する
```

保存の完了を待つ設計では、保存要求を送っただけで UI が「保存済み」と表示しないようにします。バックグラウンド保存など別の方式を選ぶ場合は、「受付済み」と「保存完了」を区別することを推奨します。

## 失敗したとき

データの取得や保存に失敗した場合も、結果は Data → Process → UI の順で返します。Data から直接ダイアログを表示する構成にはしません。

たとえば、Data は「保存先に接続できなかった」という事実を Process に伝えます。Process は「今回は保存を完了できなかった」というアプリ上の結果を決め、UI が利用者に伝える文章を選びます。

結果の値、例外、通知など、失敗を渡す技術は本初版では固定しません。ただし、使う窓口ごとに、成功時と失敗時の扱いを説明できるようにすることを推奨します。

## すべての処理が3層を通るわけではない

画面内の説明を開閉するだけなら、UI の中で完結できます。入力された値だけで計算できる機能なら、UI → Process → UI で完結できます。

必要のない層を形式的に通すのではなく、担当する仕事がある層だけを使います。ただし、必要な Data へのアクセスを UI から直接行ってよいという意味ではありません。
