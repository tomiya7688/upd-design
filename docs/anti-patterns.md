# 避けたい設計

この文書は、UPD の境界が崩れる例と、直し方を説明します。禁止事項の根拠は[基本規則](../specification/README.md)です。最後の「ひとつに集めすぎる」は推奨事項であり、コードの大きさだけで違反を決める規則ではありません。

## UI がデータベースを直接読む

**避ける例：** 検索ボタンの処理から、データベースへの問い合わせを直接実行します。

UI が保存先や取得方法まで知ることになり、Process を飛び越えます。

**直し方：** UI は Process に検索を依頼します。Process が必要なデータを Data に依頼し、結果を UI へ返します。

## Process が表示の見た目を決める

**避ける例：** Process が「文字を赤にする」「価格の末尾に円を付ける」「この画面部品を隠す」と決めます。

アプリの判断や計算が、特定の画面表示と結び付きます。

**直し方：** Process は価格や状態を値として返します。UI が文言、色、画面部品への反映を担当します。たとえば、ゲーム上の危険状態の判定は Process、その状態を赤く見せることは UI です。

## Data が業務上の結果を決める

**避ける例：** データベースの読み書き処理の中で、利用者に購入を許可するかどうかまで判断します。

業務上のルールと、保存先の操作が混ざります。

**直し方：** 購入条件は Process が判断します。Data は読み書きを行い、保存先で起きた制約違反や失敗などの事実を返します。保存先の制約を検出することと、業務上の判断を担当することは区別します。

## Shared に入れて境界を飛び越える

**避ける例：** UI から呼べる共通関数を `shared` に置き、その関数の中から Data の保存処理を呼びます。

ファイルの置き場所を変えても、UI が Process を通さずに保存していることは変わりません。

**直し方：** 共有領域には層に属さない値や型を置きます。保存の依頼は UI → Process → Data の経路に戻します。

## Commander をなくして、別名の巨大な部品を作る

**避けたい例：** Commander という名前を外した代わりに、ひとつの `Manager` や `Service` へ、無関係な処理まで集めます。

名前を変えても、仕事を分けたことにはなりません。

**直し方：** まず UI・Process・Data の所属を確認し、その中でも目的が異なる仕事を分けることを推奨します。ただし、小さな処理を必ず呼び出し役と実処理役に分ける必要はありません。形式的な部品の数より、担当する仕事が分かることを重視します。
