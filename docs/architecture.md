# 設計の全体像

この文書は、UPD を初めて読む人向けに、処理を UI・Process・Data のどこへ置くかを説明します。ここでいう「層」は仕事の種類によるまとまり、「責務」はそのまとまりが担当する仕事です。

## 商品検索で考える

利用者が検索欄に文字を入れ、検索ボタンを押す場面を考えます。

**UI は、入力と表示を担当します。** 検索欄の文字を取り出し、Process に検索を依頼します。返された商品の名前や価格を、画面に合う形に整えて表示します。

**Process は、アプリとして何をするかを決めます。** 検索条件がアプリのルールを満たすかを確認し、必要なデータを Data に依頼します。取得したデータを使い、検索結果として返す内容を決めます。

**Data は、データの読み書きを担当します。** 指定された条件に従ってデータベースやファイルから商品を読み、結果を Process に返します。画面への表示方法や、アプリの業務上の判断は決めません。

保存先を変更するときは Data、画面の見せ方を変えるときは UI、検索のルールを変えるときは Process を中心に見直せる構成を目指します。変更内容によっては、複数の層や受け渡す値の見直しも必要です。

## UI：利用者とのやり取り

UI は入力の取得、画面の状態、描画、画面遷移、表示用の整形を担当します。たとえば、価格を「1,200円」と表示することや、読み込み中の表示を出すことは UI の仕事です。

UI に置かないのは、購入できるかの最終判断、割引額の計算、データベースの直接操作などです。ボタンを押せなくする表示上の工夫だけで、業務上の検証を済ませたことにはしません。

## Process：アプリの判断と計算

Process は業務やゲームのルール、計算、処理の進め方を担当します。たとえば、購入条件の確認、割引額の計算、ゲームの勝敗判定が該当します。

Process は、画面部品やデータベースの接続方法を知る必要がありません。「商品を取得する」という依頼は扱っても、画面の色や SQL の組み立てを担当するわけではありません。

Commander を必須にしないため、小さな機能では、ひとつの関数が検証と処理の順序の両方を扱ってもかまいません。ただし、無関係な仕事まで集めず、大きくなったら目的ごとに分けることを推奨します。

## Data：データの取得と保存

Data はファイル、データベース、外部のデータ提供先などを扱います。保存形式との変換、読み書きに必要な整形、取得・保存の失敗の検出も担当します。

「購入を許可するか」は Process の判断です。一方で、保存先で重複が起きたことや、接続できなかったことを検出するのは Data の仕事です。その事実を返し、アプリとしての扱いは Process が決めます。

## 層の境界には、使ってよい窓口を決める

「窓口」は、別の層から使ってよい関数やインターフェースです。たとえば、UI から使う「商品を検索する」関数、Process から使う「条件に合う商品を取得する」関数を決めます。

窓口の名前、受け取る値、返す値、失敗時の扱いを明らかにします。別の層は、その窓口を使い、相手の内部変数や非公開の処理を直接操作しません。

本初版では、隣り合う層の公開された窓口を関数呼び出しで使う方法も選べるものとして整理しています。Commander や Messenger という名前の中継クラスを、形式のためだけに追加する必要はありません。この呼び出し方は[差分の文書](differences-from-commander-base.md)に記載した初版の整理方針です。

## 結果の流れと、コードの依存は分けて考える

```text
要求：UI → Process → Data
結果：Data → Process → UI
```

結果が逆向きに戻っても、Data が UI の画面部品を操作してよいわけではありません。関数の戻り値として結果を返すだけなら、Data が呼び出し元の具体的なクラスを知る必要はありません。

「依存」は、ほかの部品の型や実装を前提にすることです。境界を確認するときは、実際の呼び出しだけでなく、コード上の参照も確認します。

## 共有する値の置き場所

複数の層で使う、受け渡し用の値や型の定義は、必要に応じて `Common` または `Shared` に置けます。たとえば、商品情報の受け渡し用の型が該当します。

この共有領域は、4つ目の処理層ではありません。画面の描画、購入可否の判断、データベースへの接続を移してはいけません。共有領域から UI・Process・Data の具体的な実装へ依存してはいけません。この禁止事項は[基本規則](../specification/README.md)にも記載しています。

## 構成例は、名前を強制するものではない

```text
src/
├─ ui/        入力と表示
├─ process/   アプリの判断と計算
├─ data/      データの取得と保存
└─ shared/    必要な場合だけ置く、層に属さない値や型
```

これは配置の例です。特定の言語、フォルダ名、クラス名、継承関係を必須にはしません。まず担当する仕事を説明できるようにし、その境界がコードからも確認できる構成を選びます。
