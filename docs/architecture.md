# 設計の全体像

UPD は、アプリケーションの仕事を UI・Process・Data に分離します。各層が担当する仕事を「責務」と呼びます。

## UI：入力と表示

UI は、利用者の入力を受け取り、結果を表示します。入力欄から文字を読む、ボタン操作を受け付ける、読み込み中の表示を出す、結果を画面に並べるといった仕事です。

たとえば、価格を「1,200円」と表示するのは UI の担当です。一方で、割引額を決めるのは Process、価格をデータベースから取得するのは Data の担当です。

UI は、業務やゲームのルールの判断、データの読み書きを担当しません。

## Process：判断と計算

Process は、アプリのルールに従って判断し、計算や処理を進めます。購入条件の確認、割引額の計算、ゲームの勝敗判定といった仕事です。

処理にデータが必要なら、Data に取得を依頼します。処理の結果を保存する必要があれば、Data に保存を依頼します。

Process は、画面の見せ方や、データベース・ファイルの操作を担当しません。「何を取得するか」は判断しても、「どう接続して読み出すか」は Data に任せます。

## Data：取得と保存

Data は、データベース、ファイル、外部のデータ提供先などからデータを取得し、保存します。保存形式への変換や、読み書きの失敗を検出することも担当します。

Data は、画面を操作したり、購入を許可するかなどの業務上の判断を行ったりしません。読み書きの結果を Process に返します。

## 処理をどこに置くか

処理の名前ではなく、何のための仕事かで分けます。

| 仕事 | 担当する層 | 理由 |
| --- | --- | --- |
| 金額を3桁ごとに区切って表示する。 | UI | 利用者にどう見せるかを決める仕事だからです。 |
| 割引後の金額を計算する。 | Process | アプリのルールで金額を決める仕事だからです。 |
| 金額を保存先の形式に変換する。 | Data | データを書き込むための仕事だからです。 |

たとえば、入力欄の文字を読むのは UI、入力内容が購入条件を満たすか確認するのは Process です。画面上で購入ボタンを押せなくするだけでは、Process が行う条件の確認の代わりにはなりません。

## 境界を保つ

UI は Process に処理を依頼し、Process は Data に取得や保存を依頼します。UI と Data は直接やり取りしません。

層の間では、処理に必要な値を渡します。たとえば、UI から Process へ渡すのは検索文字であり、検索欄そのものではありません。Data から Process へ返すのは取得した商品情報であり、データベースの接続そのものではありません。

相手の仕事を引き受けず、それぞれの層が自分の担当を果たすことで分離を保ちます。
