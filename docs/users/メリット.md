# UPD を使うメリット

[English](en/benefits.md)

UPD は **UI・Process・Data の仕事を区別し、変更・検証・再利用をしやすくする設計**である。

以下は、責務が適切に分離されている場合に期待できる効果である。UPD の採用だけで自動的に保証されるものではない。

## 1. 変更の影響を整理しやすい

表示方法の変更では UI、アプリケーションのルールの変更では Process、取得・保存方法の変更では Data が主な確認対象となる。

例えば、商品一覧を表形式からカード形式へ変更する際、検索条件の判断やデータの取得処理まで修正する必要は通常ない。

**変更の目的から、見直すべき責務を特定しやすくなる。**

## 2. 不具合の調査範囲を絞りやすい

割引額の誤りは Process、金額の表示形式の誤りは UI、保存した注文を取得できない問題は Data が主な調査の起点となる。

原因が必ずその層に存在するとは限らないが、調査の優先順位を判断しやすい。

## 3. 責務ごとにテストしやすい

Process の判断や計算は、画面を操作せずに検証しやすい。UI は表示・返却の動作、Data は取得・保存の動作を中心に検証できる。

各層のテストに加えて層間の受け渡しを検証することで、個別の動作と全体の動作を区別して確認できる。

## 4. 画面や保存方法を変更しやすい

同じアプリケーションのルールを複数の画面や外部インターフェースから利用する場合、Process にまとめたルールを再利用しやすい。

保存先の変更も Data を中心に対応できる。ただし、受け渡す値の意味や機能仕様が変わる場合には、関連する層も変更対象となる。

## 5. 責任範囲を共有しやすい

入力・表示、ルール、保存という共通の分類により、実装やレビューで各処理の担当を明確にできる。

開発者を層ごとに分ける必要はない。単独開発でも、処理の置き場所を判断する基準となる。

## 導入に伴う負担

層の間で受け渡す値や成功・失敗の扱いを決める必要がある。小さな機能では、分離によってコードや確認作業が増える場合もある。

**境界を守らなければ、責務分離の効果は損なわれる。** UI から Data を直接操作する実装は、一時的には簡単でも変更やテストへの影響を広げる。

UPD 自体が開発速度や品質を保証するわけではない。**異なる責務を混在させないことを継続するための設計原則**である。

適性の判断には [UPD が向いているプロジェクト](向いているプロジェクト.md)、処理の具体例には [具体例で理解する UPD](具体例.md) を参照する。
