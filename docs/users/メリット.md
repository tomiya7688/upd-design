# UPD を使うメリット

[English](en/benefits.md)

UPD の目的は、**仕事の違いをコード上でも明確にすること**です。UI・Process・Data を分けることで、変更・確認・再利用をしやすくします。

以下は、責務が正しく分かれている場合に期待できるメリットです。UPD を採用するだけで、自動的に保証される効果ではありません。

## 1. 変更の影響を整理しやすい

画面の見せ方を変更するときは UI、アプリのルールを変更するときは Process、保存先や取得方法を変更するときは Data が主な確認先になります。

たとえば、商品一覧を表からカード形式に変える場合、商品を取得する処理や検索条件の判断まで書き直す必要は通常ありません。

**何のための変更かが、どの仕事を見直すべきかの手掛かりになります。**

## 2. 不具合の原因を探しやすい

「割引額が違う」のなら Process、「計算結果の表示がおかしい」のなら UI、「保存した注文が読めない」のなら Data を最初に調べられます。

原因が必ずその層にあるとは限りませんが、確認する順番を決めやすくなります。

## 3. 仕事ごとにテストしやすい

Process の計算や判定を、画面を操作せずに確認しやすくなります。UI は表示の動作を、Data は読み書きの動作を中心にテストできます。

層の間の受け渡しも別に確認すれば、個々の仕事と全体の動作の両方を確かめられます。

## 4. 画面や保存方法を変えやすい

同じアプリのルールを、別の画面から使う場合でも、Process にルールがまとまっていれば再利用しやすくなります。

同じように、保存先を変更するときは Data を中心に修正できます。ただし、受け渡す値や機能の仕様まで変わる場合は、関連する層の修正も必要です。

## 5. 複数人でも担当を共有しやすい

「表示の仕事」「ルールの仕事」「保存の仕事」という共通の整理方法があると、実装やレビューで責任範囲を相談しやすくなります。

これは担当者を必ず層ごとに分けるという意味ではありません。ひとりで開発する場合も役立ちます。

## メリットと引き換えに考えること

境界を分けると、層の間で渡す値や、成功・失敗の扱いを考える必要があります。小さな機能では、分離に伴うコードや確認作業が増えることもあります。

また、**仕事の境界を守らなければ、UPD を使うメリットは薄れます。** 画面から保存先を直接操作するなどの近道は、当初は簡単でも、変更やテストの影響を広げる原因になります。

UPD は速度や品質を保証する魔法ではありません。**異なる仕事を混ぜないという判断を、開発中も保ち続けるための設計**です。

プロジェクト規模や処理の特徴から適性を考えたい場合は、[UPD が向いているプロジェクト](向いているプロジェクト.md) を参照してください。
