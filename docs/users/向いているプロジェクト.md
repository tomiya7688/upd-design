# UPD が向いているプロジェクト

[English](en/suitable-projects.md)

UPD は、アプリケーションの仕事を **UI（入力と表示）・Process（判断と計算）・Data（取得と保存）** に分離する設計です。

**UPD の向き不向きは、単純なコード量や人数よりも、3つの仕事がどれだけ異なる理由で変更されるかによって決まります。** ここでいう小規模・中規模・大規模は、厳密な行数や開発人数の区分ではなく、考えるための目安です。

## 規模別の目安

| 規模 | UPD との相性 | 具体例と理由 |
| --- | --- | --- |
| **小規模** | **条件次第で有効** | 家計簿や個人用の記録アプリ。画面、集計ルール、保存処理を個別に変更・テストするなら価値がある。一方、単純な表示だけの小さなツールでは、分けるための作業の方が大きくなることがある。 |
| **中規模** | **特に向きやすい** | 在庫管理、予約管理、受注管理。画面が複数あり、条件判定や計算とデータの読み書きが増えるほど、担当を分けるメリットが分かりやすい。 |
| **大規模** | **有効だが UPD だけでは足りない** | ECサイトや複数部署で使う業務システム。機能ごとに UI・Process・Data の責務を分けることは役立つが、機能同士の境界、権限、並行処理、運用などは別途設計する必要がある。 |

**結論として、中規模の業務アプリケーションは UPD の効果を感じやすい例です。** ただし、小規模でも判断や保存が複雑なら有効であり、大規模でも責務分離の価値は変わりません。

## どんな処理が多いと向いているか

### 1. 条件判定・計算などのルールが多い

割引、手数料、在庫引当、予約可否、ゲームの勝敗判定など、**画面の表示とは別に判断すべき処理**が多い場合です。

例えば料金の計算方法を変更するとき、計算を Process にまとめておけば、画面の表示処理やデータの保存処理と分けて確認しやすくなります。

### 2. 同じルールを複数の画面から使う

Web画面と管理画面など、**入力方法や表示方法は違っても、同じ判断を使う**場合です。

UI の見た目を変えても、Process にある購入条件や計算のルールを再利用しやすくなります。

### 3. データの取得先・保存先が複数ある、または変わりやすい

データベース、CSV、外部APIなどを組み合わせる場合です。

Data が読み込みや保存を引き受け、**取得元ごとの形式の違いを正規化**すれば、Process はデータソースの細部を意識せずに判断を行いやすくなります。ただし、値に業務上の意味を与える補完や判定は Process の仕事です。

### 4. 成功・失敗の扱いやテストが重要

注文保存、予約確定、記録更新など、**保存に成功したか、失敗した場合どう扱うか**を区別する必要がある場合です。

Data は読み書きの結果を返し、Process はアプリとしての対応を決め、UI は利用者へ表示します。責務が分かれていると、それぞれの動作と層をまたぐ動作を確認しやすくなります。

## プロジェクトの具体例

| プロジェクト | UI | Process | Data |
| --- | --- | --- | --- |
| **家計簿アプリ（小〜中規模）** | 支出入力、集計結果の表示 | 費目別集計、予算超過の判定 | 記録の保存、CSV取込時の形式統一 |
| **在庫・受発注管理（中規模）** | 商品検索、注文入力、在庫一覧 | 発注可否、在庫引当、金額計算 | 在庫・注文の取得と保存 |
| **予約管理（中〜大規模）** | 日時選択、予約状況の表示 | 受付条件、空き枠の判定 | 予約データの取得と保存 |
| **ECサイト（大規模）** | 商品画面、カート、決済結果の表示 | クーポン条件、金額計算、注文の判断 | 商品・注文・顧客データの読み書き |
| **セーブ機能のあるゲーム（規模を問わない）** | プレイヤー入力、勝敗や画面の表示 | ゲームのルール、得点・勝敗計算 | セーブデータの読み書き |

これらは **UPD の使い方を説明する例**であり、業種や規模だけで採用を決めるものではありません。

## 向きにくい、または効果が小さい場合

- **ほぼ表示だけの静的なページ**：業務判断も保存もほとんどなく、分ける仕事が少ない。
- **一度きりの短い変換スクリプト**：入力から出力までの処理が単純で、責務を分ける費用が効果を上回ることがある。
- **単純な1画面の試作品**：画面と少量の処理だけで完結し、今後の変更も少ないなら効果が見えにくい。

ただし、単純に見える機能でもルールが増えたり、データソースが変わったりする予定なら、UPD の分離が役立つことがあります。

**UPD を採用しない選択と、採用したのに境界を破ることは別です。** 採用した場合は、規模にかかわらず [境界の規則](../developers/境界.md) を守ります。

## 採用を考えるときの確認点

- 画面の表示方法、アプリのルール、データの取得・保存方法は、それぞれ独立して変更されそうか。
- 業務上の判断や計算を、画面やデータソースから切り離してテストしたいか。
- 同じルールを複数の画面から使ったり、複数のデータソースを扱ったりするか。
- 境界を保つための設計・テストの手間に見合う効果があるか。

**特に「表示・判断・読み書きがそれぞれ変わる」「判断や計算が多い」プロジェクトなら、UPD は検討しやすい設計です。**
