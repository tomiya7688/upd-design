# 具体例で理解する UPD

[English](en/examples.md)

UPD では、1つの機能を **入力・判断・データの読み書き・結果の表示** に分け、それぞれの責務を明確にする。

## 例1：商品検索

利用者が検索欄に文字を入力し、検索を実行する場合を考える。

| 手順 | 担当 | 処理 |
| --- | --- | --- |
| 1 | UI | 検索欄から文字を受け取る |
| 2 | Process | 検索条件を確認する |
| 3 | Data | 条件に合う商品を取得する |
| 4 | Process | アプリケーションのルールに従って結果を整理する |
| 5 | UI | 商品一覧を表示する |

検索順位をアプリケーションのルールで決める場合は Process が担当する。一方、カード表示か表形式かといった画面上の配置は UI が決める。

## 例2：注文の保存

購入ボタンが押された場合、UI は商品と数量を Process に渡す。

Process は購入条件を確認し、必要な計算を行ったうえで、保存する内容を決める。Data はその内容を保存し、結果を Process に返す。Process は保存結果を解釈し、UI は結果を表示する。

**保存の依頼と保存の完了は異なる。** 保存完了が確認される前に、UI が成功と表示してはならない。

## 例3：ゲームの勝敗表示

UI はプレイヤーの操作を受け付ける。Process はゲームのルールに基づいて勝敗を判定し、UI が結果を表示する。

記録を保存する場合に限り、Process は Data に保存を依頼する。保存が不要な処理に Data を経由させる必要はない。

## 境界違反の例

- UI が直接データベースから商品を取得する。
- UI が購入の可否や割引条件を最終判断する。
- Data がゲームの勝敗を判定する。
- Process が画面の色や配置を変更する。

いずれも、担当外の責務を引き受ける実装である。

## 要点

**「検索」「購入」といった機能単位で分割するだけでは不十分である。** 1つの機能に含まれる異なる仕事も、それぞれの層に分離する。

適性の判断は [UPD が向いているプロジェクト](向いているプロジェクト.md)、必須規則は [開発者向けの境界規則](../developers/境界.md) を参照する。
