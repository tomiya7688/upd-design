# UPD の考え方（利用者向け）

UPD は、アプリケーションの仕事を **UI・Process・Data** に分ける設計です。「層」とは、仕事の種類によって分けたまとまりのことです。

UPD はアプリケーションやライブラリの名前ではありません。**どんな仕事を、どの層が引き受けるか**を明確にするための考え方です。

## なぜ3つに分けるのか

ひとつの処理に、画面の操作、アプリの判断、保存先の操作が混ざると、小さな変更でも関係のない処理を確認しなければなりません。

UPD は、変更する理由が異なる仕事を分けます。

| 仕事 | 担当 | 具体例 |
| --- | --- | --- |
| 利用者とのやり取り | **UI** | ボタンの操作を受け取る、結果を画面に表示する |
| アプリの判断や計算 | **Process** | 購入可能かを判定する、割引額を計算する |
| データの読み書き | **Data** | 商品を検索する、注文情報を保存する |

たとえば「割引額を計算すること」と「割引後の金額を赤字で表示すること」は違う仕事です。計算は Process、表示は UI に分けます。

## 仕事の境界を守る

**UPD を採用するなら、3つの層の境界を破ってはいけません。**

UI はデータを自分で読み書きせず、Process に必要な処理を依頼します。Process はアプリとして何をするか判断し、データが必要なら Data に依頼します。Data は取得・保存の結果を Process に返し、最終的な表示は UI が担当します。

    UI → Process → Data
    UI ← Process ← Data

これは「すべての操作が必ず3層を通る」という意味ではありません。説明文の開閉なら UI だけで終わります。データを必要としない計算なら UI と Process だけで完結できます。

**重要なのは、担当外の仕事を別の層が行わないことです。** フォルダだけ分けても、処理が混ざったままなら UPD の分離にはなりません。

## この考え方で何が得られるか

役割を分けると、画面、アプリのルール、データの保存方法をそれぞれ見直しやすくなります。テストの対象や、不具合が起きた場所も絞り込みやすくなります。

ただし、分けただけですべての変更が一箇所で済むわけではありません。層の間で渡すデータや、機能全体にかかわる仕様が変わる場合は複数の層に変更が必要です。
