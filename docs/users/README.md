# UPD の考え方（利用者向け）

[English](en/README.md)

UPD は、アプリケーションの仕事を **UI・Process・Data** に分ける設計である。「層」とは、担当する仕事の種類によって分けたまとまりを指す。

UPD はアプリケーションやライブラリではなく、**仕事の担当と境界を定める考え方**である。

## 適用範囲

UPD は、外部とのインターフェースを持つプロジェクトを対象とする。UI の相手は人間に限らず、機器やほかのシステムも含む。

外部との接点を持たず、内部だけで自律的に完結するプロジェクトには適さない。

## 3つの責務

画面や外部システムとのやり取り、アプリケーションの判断、データの読み書きが1つの処理に混在すると、変更の影響範囲が広がりやすい。UPD では、変更の理由が異なる仕事を分離する。

| 仕事 | 担当 | 例 |
| --- | --- | --- |
| 外部とのやり取り | **UI** | ボタンや外部システムから要求を受け取り、結果を返す |
| アプリケーションの判断・計算 | **Process** | 購入の可否を判定し、割引額を計算する |
| データの取得・保存 | **Data** | 商品情報を取得し、注文情報を保存する |

例えば、割引額の計算は Process、割引後の価格を赤字で表示する処理は UI が担当する。

## 境界の原則

**UPD を採用する場合、各層は担当外の仕事を行ってはならない。**

UI は処理を Process に依頼する。Process はルールに従って判断し、必要に応じて Data に取得や保存を依頼する。Data は結果を Process に返し、UI が結果を表示・返却する。

    要求：UI → Process → Data
    結果：Data → Process → UI

すべての操作が3層を経由する必要はない。説明文の開閉は UI 内で完結し、データを使わない計算は UI と Process だけで完結する。

**重要なのは、必要な層だけを使い、その境界を破らないことである。** フォルダだけの分割は責務の分離に当たらない。

## 分離による効果

表示方法、アプリケーションのルール、データの保存方法をそれぞれ見直しやすくなる。テスト対象と不具合の調査範囲も絞り込みやすい。

ただし、層の間で受け渡すデータや機能の仕様が変わる場合には、複数の層に変更が及ぶ。

具体的な効果は [UPD を使うメリット](メリット.md) に示す。

## 向いているプロジェクト

適用の前提は、**外部とのインターフェースがあること**である。そのうえで、規模ではなく分離すべき仕事の有無を判断する。詳しくは [UPD が向いているプロジェクト](向いているプロジェクト.md) に示す。
