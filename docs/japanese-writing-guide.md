# 日本語文書の書き方

この文書は、UPD Design の説明を追加・修正するときの執筆基準です。初めて読む人が、何をどこに置けばよいかを判断できる説明を目指します。

## 最初に、何が分かる文書かを書く

冒頭で対象読者と目的を説明します。基本の順序は「結論や全体像 → 具体例 → 理由 → 条件や例外」です。読む前から別の仕様を詳しく知っていることを前提にしません。

ひとつの段落では、ひとつの話題を扱います。主語を省くと担当が分からなくなる場合は、「UI は」「Process は」「Data は」と書きます。

## 用語に短い説明を付ける

専門用語は、最初に使う場所で意味を説明します。

| 用語 | 説明の例 |
| --- | --- |
| 層 | 担当する仕事の種類によるまとまり。 |
| 責務 | その部品が担当する仕事。 |
| 依存 | ほかの部品の型や実装を前提にすること。 |
| 窓口 | 別の層から使ってよい関数やインターフェース。 |
| 契約 | 受け取る値、返す値、失敗時の扱いについての取り決め。 |

`UI`、`Process`、`Data` は層の名前として表記をそろえます。一般的な情報を指す「データ」と、担当する層を指す `Data` は区別します。

英語の名称が必要な場合も、日本語の説明を先に置きます。「契約に従う」だけで済ませず、どの値を渡し、何が返るのかを説明します。

## 「すること」と「しないこと」を対にする

「UI は表示を担当する」だけで終えず、「価格の文字列を整えるのは UI、割引額を決めるのは Process」のように境界の両側を示します。

一般アプリの例とゲームの例を使えますが、例だけで適用対象を狭めません。商品検索だけに使う設計でも、ゲーム専用の設計でもないことが伝わるようにします。

## 規則、推奨、例を混ぜない

必須規則には「守る」「してはいけない」を使います。推奨事項には「推奨する」を使い、採用しない場合の考え方も説明します。実装例のクラス名やフォルダ名を、説明なしに必須条件へ変えません。

規則の基準は[基本規則](../specification/README.md)です。規則の強さを変える場合は、README と関連文書も合わせて確認します。

依頼で指定されたこと、初版で採った整理方針、まだ決まっていないことも区別します。提案を「決定済み」と書いたり、存在しない実装やチェッカーを「利用できる」と書いたりしません。

## 分かりにくい文を書き直す

**説明不足：** 層間の責務境界を保って処理を委譲する。

**書き直し例：** UI は Process に検索を依頼します。データベースから商品を読む処理は Data が担当します。UI は Data を直接呼びません。

**誤解を招く例：** Commander は不要なので、別の層を直接呼んでもよい。

**書き直し例：** Commander は必須にしません。ただし、UI が Data を直接呼ぶことは禁止です。隣り合う層の呼び出し方は、基本規則の初版方針に従います。

## 更新時に確認する

読者が冒頭から理解できるか、専門用語を説明したか、各層の担当が分かるかを確認します。さらに、必須規則と推奨事項を混同していないか、未決定の内容を断定していないか、リンク先が存在するかを確認します。

元の設計との関係を変更した場合は、[差分の文書](differences-from-commander-base.md)も更新します。説明文書は `docs/`、守る規則は `specification/` に置き、同じ規則に矛盾する定義を増やさないようにします。
