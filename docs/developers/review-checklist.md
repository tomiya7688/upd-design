# レビューのチェックリスト

このチェックリストは、UPD を使った実装・変更のレビューで、責務の境界が守られているか確認するためのものです。

**重要：必須の境界規則は、チェック項目を省略しても変わりません。** 詳細は [必ず守る境界](boundaries.md) を参照してください。

## UI

- [ ] 入力の取得と表示を担当している。
- [ ] 業務・ゲームのルールの最終判断や計算が UI に入っていない。
- [ ] データの取得や保存を UI が直接行っていない。
- [ ] Process に画面部品を操作させていない。

## Process

- [ ] アプリのルールに基づく判断・計算が Process に置かれている。
- [ ] Process が画面や表示用の部品を操作していない。
- [ ] Process がデータベースやファイルの読み書きを直接行っていない。
- [ ] データの取得・保存が必要なら Data に依頼している。

## Data

- [ ] Data が取得・保存と、それに必要な変換や失敗の検出を担当している。
- [ ] Data がアプリのルールの判断を行っていない。
- [ ] Data が画面の表示や UI への直接通知を行っていない。

## 層をまたぐやり取り

- [ ] UI と Data の間に直接の要求・結果通知がない。
- [ ] 共通関数やイベントなどを経由して、実質的に境界を飛び越えていない。
- [ ] 各層に必要な値や結果だけが受け渡され、他層の内部処理を任されていない。
- [ ] 成功時だけでなく、失敗時にも責務を分けている。
- [ ] 処理の名前や配置だけでなく、**実際に何の仕事をしているか**を確認した。

## 分離の効果も確認する

次の項目は必須の違反判定ではなく、設計を見直す目安です。

- [ ] 画面の見せ方だけを変えるとき、アプリの判断処理まで変更しなくて済むか。
- [ ] アプリのルールを変更するとき、保存先の実装から切り離して確認しやすいか。
- [ ] Data の読み書きを変えるとき、UI の表示処理への影響を説明できるか。
- [ ] 各層のテストと、層の間の受け渡しのテストを考えられるか。

機能によっては複数の層に変更が必要です。その場合も、「変更の理由」と「その層が担当する仕事」を説明できることが大切です。
