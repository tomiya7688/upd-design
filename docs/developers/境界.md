# 必ず守る境界

[English](en/boundaries.md)

**UPD では UI・Process・Data の責務を越えてはいけません。** この文書の「禁止」は、処理が小さい場合や、一時的な実装であっても同じです。

ただし、UPD は層の内部に置くクラスの種類や、層の間の技術的な連携方法を決めるものではありません。ここで定めるのは、**どの層が何の仕事をするか**という境界です。

## 規則1：UI がアプリのルールを決めてはいけない

UI の担当は入力と表示です。業務・ゲームのルールに基づく最終判断や計算を、UI に置いてはいけません。

**違反例：** 購入ボタンのイベント処理が、会員ランクを判定し、割引額を計算して注文を確定する。

**分離した例：** UI は購入の入力値を Process に渡し、Process が購入条件の判定と金額の計算を行い、UI が結果を表示する。

入力欄を空欄として強調するなど、表示上の反応は UI の仕事です。しかし、見た目上の入力チェックだけを、購入などの最終的な条件判定の代わりにしてはいけません。

## 規則2：Process が表示や保存先の操作をしてはいけない

Process はルールと計算を担当します。画面部品の描画や操作、データベース・ファイルの読み書きを自分で担当してはいけません。

**違反例：** Process が画面の文字色を変更する。あるいは Process の判断処理に SQL やファイルの書き込みが混ざる。

**分離した例：** Process はアプリの状態を値として UI に返します。データの取得・保存が必要なときは Data に依頼します。

「保存すべきか」を判断するのは Process、「どう保存するか」は Data の仕事です。

## 規則3：Data がアプリの判断や表示をしてはいけない

Data はデータの読み書きが担当です。購入の許可、ゲームの勝敗などのアプリのルールを決めたり、画面を操作したりしてはいけません。

**違反例：** データ取得処理が会員の購入資格を最終判断し、画面に警告を表示する。

**分離した例：** Data は判断に必要なデータや読み書きの結果を返します。Process がアプリとしてどう扱うか決め、UI が表示します。

保存先の一意制約への違反や接続失敗など、**読み書きに関する事実を検出することは Data の仕事**です。その事実をアプリとしてどう扱うかは Process が決めます。

## 規則4：UI と Data を直接つないではいけない

UI が Data にデータを直接要求してはいけません。Data が UI に結果を直接通知・反映してもいけません。

    〇 UI → Process → Data
    〇 Data → Process → UI
    × UI → Data
    × Data → UI

**違反例：** 画面のボタンからデータベースを呼ぶ。あるいは Data が画面を更新する通知を UI に直接届ける。

**分離した例：** UI のデータ要求は Process を通します。Data からの結果・失敗も Process が受け取り、UI へ返します。

非同期通知やイベントを使っても同じです。**通信経路の名前を変えても、仕事を飛び越えることは認めません。**

## 規則5：間に部品を置いて境界をすり抜けてはいけない

共通関数、共有オブジェクト、イベントの仕組みなどを間に置いても、実質的に別の層の仕事を行わせるなら境界違反です。

**違反例：** UI から共通の便利関数を呼び、その中で Data に直接保存する。

**分離した例：** 共通の値や型を使うことはできます。ただし、UI からの保存要求は Process が判断し、Data が保存する構成を保ちます。

名前やフォルダの位置ではなく、**実際の要求と処理がどこを通っているか**で判断してください。

## 規則6：層の内部のものを、別の層の仕事の代わりに渡してはいけない

層の間では、その処理に必要な値や結果を受け渡します。

**違反例：** UI の画面部品そのものを Process に渡して操作させる。Data が接続オブジェクトを UI に渡し、UI に読み書きさせる。

**分離した例：** UI は検索文字などの値を Process に渡します。Data は商品情報や保存結果を返します。

## 規則7：取得したデータの正規化は Data、意味の判断は Process が担当する

**Data は、読み込んだデータを Process が扱える共通の形式に正規化してよいものとします。** これはデータの取得・読み書きに伴う仕事です。

**Data に置く処理の例：**

- JSON や CSV から定義済みの型へ変換する。
- データソースごとの項目名を共通の項目名に対応付ける。
- スキーマに従って数値や日付の表現を統一する。
- 文字コードや、意味を変えない範囲で文字の表現を統一する。
- 解析できない値や欠損を検出し、事実として Process へ返す。

**Process に置く処理の例：**

- 会員ランクに応じて金額を変更する。
- 欠損した値に、アプリのルールで決めた初期値を当てはめる。
- 取得した情報から購入可否やゲームの勝敗を判断する。
- アプリのルールに従ってデータを選別・優先順位付けする。

**境界は「形式をそろえるか、業務上の意味を決めるか」です。** Data の正規化では、元データの意味を勝手に変更したり、欠損や不正な値を業務ルールに従って黙って補ったりしてはいけません。

例えば外部サービスの `price` が文字列 `"1200"` で返る場合、定義済みの数値型へ変換するのは Data です。一方、そこから会員割引を適用して支払金額を計算するのは Process です。

保存する際の保存形式への変換も Data が担当しますが、**何を保存してよいかを決めるのは Process** です。

## 成功・失敗のどちらでも守る

正常時は分離していても、失敗時だけ Data が直接ダイアログを出す、UI が自動再保存をするなど、担当外の仕事を引き受けてはいけません。

たとえば保存に失敗した場合、Data が失敗の事実を Process に伝え、Process がアプリとしての結果を決め、UI が案内を表示します。

## 境界を守ることと、方式を固定することは別

これらの規則は、特定の中継部品やクラス構成を要求するものではありません。関数、インターフェース、イベントなどをどう使うかはプロジェクトで決められます。

ただし、**どの方式でも、UI・Process・Data の責務と UI／Data の間の境界は破れません。**
