# 必ず守る境界

[English](en/boundaries.md)

**UPD では UI・Process・Data の責務を越えてはならない。** この規則は、小規模な機能や一時的な実装にも適用する。

本書は各層の責務と禁止事項を定める。クラス構成、関数の形、層間の通信技術は規定しない。

## 規則1：UI にアプリケーションの判断を置かない

UI は、外部からの要求を受け付け、結果を返す。画面がある場合は表示も担当する。相手は人間、機器、ほかのシステムのいずれでもよい。

**UI は、業務・ゲームのルールに基づく最終判断や計算を行ってはならない。**

**違反例：** 購入ボタンの処理内で会員ランクを判定し、割引額を計算して注文を確定する。

**適切な分離：** UI が購入に必要な値を Process に渡し、Process が購入条件の判定と金額計算を行う。UI は返された結果を表示する。

入力欄の空欄を強調するなど、表示上の反応は UI の責務である。ただし、UI の入力チェックを購入条件などの最終判定の代わりにしてはならない。

## 規則2：Process に画面操作やデータの読み書きを置かない

Process は、アプリケーションのルールに基づく判断と計算を担当する。

**Process は、画面部品を直接操作したり、データベースやファイルを直接読み書きしたりしてはならない。**

**違反例：** Process が文字色を変更する。または Process の判断処理に SQL の実行やファイルへの書き込みを含める。

**適切な分離：** Process はアプリケーションの状態を値として UI に返し、データの取得・保存を Data に依頼する。

保存の要否を判断するのは Process、保存方法を扱うのは Data である。

## 規則3：Data にアプリケーションの判断や表示を置かない

Data はデータの取得・保存と、それに伴う形式変換や入出力結果の検出を担当する。

**Data は、購入可否やゲームの勝敗などの業務上の判断を行ったり、画面を操作したりしてはならない。**

**違反例：** データ取得処理が会員の購入資格を判定し、画面に警告を表示する。

**適切な分離：** Data は判断に必要な情報と入出力の結果を Process に返す。Process がアプリケーションとしての対応を決め、UI が結果を表示する。

保存先の一意制約違反や接続失敗を検出することは Data の責務である。その事実をアプリケーション上どう扱うかは Process が決める。

## 規則4：UI と Data を直接接続しない

**UI から Data への直接的な要求、および Data から UI への直接的な結果通知・操作は禁止する。**

    許可：UI → Process → Data
    許可：Data → Process → UI
    禁止：UI → Data
    禁止：Data → UI

**違反例：** 画面のボタンからデータベースを直接操作する。または Data が UI に画面更新を直接通知する。

**適切な分離：** UI の要求は Process を経由し、Data の成功・失敗も Process が受け取って UI に返す。

**非同期通知やイベントを使用しても、この境界を迂回してはならない。**

## 規則5：中間の部品で境界を迂回しない

共通関数、共有オブジェクト、イベントなどを経由しても、実質的に別の層の仕事を直接実行する構成は境界違反である。

**違反例：** UI が共通関数を呼び、その関数が Process を経由せずに Data へ保存を依頼する。

**適切な分離：** 共通の値や型は利用できる。ただし、保存要求については Process がアプリケーション上の判断を行い、Data が保存を実行する。

判定基準は部品の名前や配置ではなく、**実際の処理経路と責務**である。

## 規則6：他層の内部処理を代行させない

層の間では、処理に必要な値と結果を受け渡す。

**他層の内部部品を渡し、その層の仕事を別の層に実行させてはならない。**

**違反例：** UI の画面部品を Process に渡して操作させる。または Data の接続オブジェクトを UI に渡して読み書きさせる。

**適切な分離：** UI は検索文字を Process に渡す。Data は取得した商品情報や保存結果を Process に返す。

## 規則7：Data の正規化と Process の判断を区別する

**Data は、取得したデータの形式を統一し、Process が扱える値へ正規化できる。** これはデータの読み込みに伴う責務である。

**Data に属する処理：**

- JSON や CSV の値を定義済みの型に変換する。
- 取得元ごとの項目名を共通の項目名に対応付ける。
- 定義済みのスキーマに従って数値・日付の表現を統一する。
- 元データの意味を変えずに文字コードや文字表現を統一する。
- 値の欠損や解析失敗を検出し、その事実を Process に返す。

**Process に属する処理：**

- 会員ランクに応じて金額を変更する。
- 欠損値をアプリケーションのルールで定めた初期値に補完する。
- 購入可否やゲームの勝敗を判断する。
- アプリケーションのルールに従ってデータを選別・優先順位付けする。

**形式の統一は Data、業務上の意味を決める処理は Process の責務である。**

Data は、元データの意味を独自に変更したり、不正な値や欠損値を業務ルールによって黙って補ったりしてはならない。

例えば外部サービスの `price` が文字列 `"1200"` である場合、定義済みの数値型への変換は Data が行う。その値から会員割引を計算する処理は Process が行う。

保存形式への変換も Data の責務である。ただし、保存する内容と保存の可否は Process が決める。

## 正常時・失敗時の共通規則

**処理が失敗した場合も、責務境界を維持しなければならない。**

例えば保存失敗時、Data が UI に直接ダイアログを表示することや、UI が業務上の再保存を独自に判断することは禁止する。Data が失敗の事実を Process に伝え、Process がアプリケーションとしての結果を決め、UI が結果を表示・返却する。

## 実装方式との関係

本書の規則は、特定の中継部品やクラス構成を要求しない。関数、インターフェース、イベントなどの採用はプロジェクト側で決める。

**方式の選択にかかわらず、UI・Process・Data の責務と UI／Data 間の境界は必ず守る。**
