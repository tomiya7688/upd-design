# 処理の分け方と受け渡し

[English](en/implementation.md)

実装の最初に、「この処理の目的は何か」を確認します。UPD は処理の名前やコードの形ではなく、**仕事の意味**で層を分けます。

## 処理の担当を決める

次の順に考えると、置き場所を判断しやすくなります。

1. **入力を受け取る、見せ方を変える仕事か？** それなら UI。
2. **アプリのルールで判断・計算する仕事か？** それなら Process。
3. **データを取得・保存する仕事か？** それなら Data。
4. **複数に当てはまるか？** 処理を仕事ごとに分け、それぞれの層に置く。

例えば「変換」という名前だけでは担当は決まりません。

| 処理 | 層 | 判断理由 |
| --- | --- | --- |
| 金額を「1,200円」と表示するために整形する | UI | 見せ方のため |
| 会員ランクに応じて割引額を計算する | Process | アプリのルールのため |
| 日付を保存先の形式に変換する | Data | データの読み書きのため |
| 取得したJSONの数値文字列を、定義済みの数値型へ変換する | Data | 取得データの表現を統一するため |
| 不足した金額をアプリのルールで補う | Process | 値の意味を決める判断だから |
| 画面でローディングを見せる | UI | 表示の状態だから |
| 保存するかどうかを決める | Process | ルール上の判断だから |
| 保存失敗を検出する | Data | 読み書きの結果だから |

## 読み込んだデータの正規化

**読み込み元による形式の違いを吸収する処理は Data に置きます。** 例えば、CSVの列名やJSONの項目名を統一したり、定義済みの形式に従って文字列を数値・日付に変換したりする処理です。Data が正規化済みの値を Process に返すことで、Process はデータの取得元の形式を意識せずにアプリのルールを実行できます。

ただし、**値の意味を変える判断は Process** です。例えば空欄を会員ランク「一般」とみなす、価格に割引を適用する、データを業務上の優先度で並べるといった処理は、正規化と呼んでも Process が担当します。

形式を解釈できない場合やデータが欠損している場合、Data はその事実を返し、アプリとしてどう扱うかは Process が決めます。意味が定まらない変換を Data が推測してはいけません。

書き込み時も同様に、保存形式への変換は Data、保存内容を決める判断は Process の仕事です。

この境界は [必ず守る境界の規則7](境界.md) に定めています。

## 商品検索のやり取り

    UI：検索文字を受け取る
      ↓
    Process：条件を確認する
      ↓
    Data：商品情報を取得し、必要な形式の正規化を行う
      ↓
    Process：アプリとして返す結果を決める
      ↓
    UI：画面に表示する

UI から Process に渡すのは、検索欄という画面の部品ではなく検索文字です。Data から Process に返すのは、接続先の内部情報ではなく取得した商品情報です。

検索条件が不正なら、Process だけで結果を決め、Data を呼ばずに UI へ返すこともできます。

## 保存時のやり取り

    UI：入力内容を渡す
      ↓
    Process：保存してよい内容か判断する
      ↓
    Data：保存を実行し、結果を返す
      ↓
    Process：結果をアプリとして解釈する
      ↓
    UI：結果を表示する

Process が「保存すべき」と判断することと、Data が「保存できた」ことは別です。保存処理を要求しただけで成功と表示しないように、完了と失敗の区別を明確にします。

## 失敗を返すとき

Data は接続失敗などの事実を返します。Process は、アプリとして再試行の対象か、失敗として返すかなどを判断します。UI は、受け取った結果を利用者にどう見せるか決めます。

返り値、例外、非同期通知など、結果を渡す技術的な方法は問いません。ただし失敗時にも **Data → Process → UI** の責務の流れを維持します。

## 層を分けたあとに決めること

具体的なファイル配置やクラス名、関数の数、通信方式は、この設計の中心ではありません。実装時には、層の間で受け渡す入力・結果・失敗を分かるようにしておくと確認しやすくなります。

また、各層の仕事を個別にテストしたうえで、全体の受け渡しが正しく動くかを確認すると、境界が維持できているかを判断しやすくなります。

必須の禁止事項は [必ず守る境界](境界.md) を、確認に使う項目は [レビューのチェックリスト](レビュー.md) を参照してください。
