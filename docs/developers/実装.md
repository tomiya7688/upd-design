# 処理の分け方と受け渡し

[English](en/implementation.md)

処理の担当層は、関数名やコードの形ではなく、**その処理の目的**によって判断する。

## 処理の分類

複数の責務が1つの処理に含まれる場合は、仕事の種類ごとに分割する。

| 処理 | 担当層 | 分類の根拠 |
| --- | --- | --- |
| 金額を「1,200円」と表示するために整形する | UI | 表示上の形式 |
| 会員ランクに応じて割引額を計算する | Process | アプリケーションのルール |
| 日付を保存先の形式に変換する | Data | 保存のための形式変換 |
| 取得した JSON の数値文字列を定義済みの数値型に変換する | Data | 取得データの形式の統一 |
| 不足した金額をアプリケーションのルールで補う | Process | 値の意味に関する判断 |
| 読み込み中であることを画面に表示する | UI | 表示状態 |
| 保存の可否を決める | Process | アプリケーション上の判断 |
| 保存失敗を検出する | Data | 入出力の結果 |

「変換」「検証」などの処理名だけでは所属を決定できない。**何のための変換・検証か**で判定する。

## 取得データの正規化

**取得元ごとのデータ形式の差異を吸収する処理は Data が担当する。**

例えば、CSV の列名や JSON の項目名を共通の項目名に対応付け、定義済みのスキーマに従って文字列を数値・日付に変換する。Data が正規化した値を返すことで、Process は取得元の形式に依存せずにアプリケーションのルールを扱える。

一方、空欄を会員ランク「一般」とみなす、価格に割引を適用する、業務上の優先順位で並べるといった処理は **Process の責務**である。正規化という名称であっても、値の意味を決める処理は Data に置いてはならない。

欠損や解析失敗は Data が事実として返し、その扱いを Process が判断する。Data が不明な値の意味を推測して補完することは禁止する。

書き込み時は、保存形式への変換を Data、保存する内容の判断を Process が担当する。

詳細は [必ず守る境界の規則7](境界.md) に定める。

## 商品検索

    UI：検索文字を受け取る
      ↓
    Process：検索条件を確認する
      ↓
    Data：商品情報を取得し、必要に応じて形式を正規化する
      ↓
    Process：アプリケーションのルールに従って結果を決める
      ↓
    UI：結果を表示する

UI が渡すのは検索欄そのものではなく検索文字である。Data が返すのは接続オブジェクトではなく、取得した商品情報である。

検索条件を満たさない場合、Process は Data を呼び出さずに結果を UI に返せる。

## データの保存

    UI：入力値を渡す
      ↓
    Process：保存の可否と内容を決める
      ↓
    Data：保存を実行し、結果を返す
      ↓
    Process：保存結果をアプリケーションとして解釈する
      ↓
    UI：結果を表示する

**保存の依頼と保存の成功は別の事実である。** 完了を確認する前に、UI が保存成功を表示してはならない。

## 失敗時の受け渡し

Data は接続失敗などの事実を Process に返す。Process が再試行や失敗の扱いを判断し、UI が結果を表示・返却する。

戻り値、例外、非同期通知など、技術的な実現方法は規定しない。ただし、**失敗時も Data → Process → UI の責務上の流れを維持する。**

## 実装時に定める事項

UPD はファイル配置、クラス名、関数の数、通信方式を固定しない。実装では、層間で受け渡す値・結果・失敗を明確にすることが重要である。

各層の処理と層間の受け渡しを別々に検証することで、境界の維持を確認しやすくなる。

必須条件は [必ず守る境界](境界.md)、レビュー時の確認事項は [チェックリスト](レビュー.md) に示す。
